# AGENTS.md

## Prototype approach

The interactive prototype exists to settle exact details in discussion, so it is built for fast iteration.

**Use: HTML/CSS skeleton, with JS populating and modifying content dynamically.** No server, no database, no build step.

### Why

- The open questions are about state changes: review comments, old-vs-new template comparison, a new reference id on re-approval, validation (length, button text), and role-based views. A fully static page can only fake these with duplicated screens.
- Mock data (templates, versions, users, roles, statuses) lives in one JS object and the UI renders from it. A new field, status or validation rule is a small edit in one place.
- State persists in `localStorage`, so reviewers can click through create → validate → review → approve → send and keep their place.
- It runs by opening the file, or can be published as a shareable artifact.

### Rules

- Keep **data and rendering separate**. If a backend is needed later, the data object becomes the API contract and the UI barely changes.
- Start with the template lifecycle (create → validate → review → approve → send) and the old-vs-new comparison, with a role switcher (Creator, Reviewer, Admin).
- Wrap every `localStorage` read and write in try/catch, and make the page work without it.

### Options not chosen (for now)

- **Fully static (HTML/CSS/JS only):** fastest to edit, but cannot show state changes.
- **Server, no DB:** only worth it if the prototype must really call Turn.io (e.g. submit templates for approval, send a test message). The Bearer token must stay server-side, so add a thin proxy at that point, not up front.
- **Server and DB:** slowest (schema, migrations, seeding) and locks in decisions that are not made yet. Defer until the data model settles.

## Prototype: Content Studio (`prototype/`)

Open `prototype/index.html` directly in a browser. There is no build step or server.

- `store.js`: all data and rules (no DOM code, testable in Node with `require`). State is saved to `localStorage`; "Reset demo data" reloads the seed.
- `app.js`: rendering and events. `style.css`: styles.

Decisions to keep consistent:

- **Model:** content is identified by a **name**; under it sit **translations** (one per language code). Each translation has the body `text` (with **named** placeholders), `defaults`, `header`, `footer`, `buttons`, `waName` (`wa_template_name`) and publish bookkeeping (`deployedText`, `deployedSig`). The name has one `headerType`. See "WhatsApp template parts" below. Templates also have a `timing`, and `state.flows` holds the flows (see "Flows" below).
- **Single user:** every action is logged as `CURRENT_USER` in `store.js` (history = who, when, what, before/after).
- **Terminology: the UI says "Publish" (Publish all, Published, Not published, Edited since publish), never "Deploy".** Internal identifiers keep the old word on purpose (`Store.deployAll`, `deployCounter`, `deployedText`, the `'deployed'` history action, `data-action="deploy-all"`) because they are persisted in `localStorage`; renaming them would break saved data. Use "Publish" in any new user-facing text.
- **Publishing is fake, and only "Publish all" exists in the UI** (name level, no per-language button). It sets `wa_template_name` to `<slug of name>_v<n>` on every language that is non-empty and not yet published (or edited since). `n` is a per-content counter that goes up by one per click, so all languages published together share one name. `wa_template_name` stays empty until the first publish. Unsaved edits are not published. (`Store.deploy` for a single language still exists in `store.js` but nothing calls it.)
- **Languages: every language of a name is an editing panel, all in one horizontal strip** (English first, then the others in the order they were added; each panel is `--panel-w` wide, the strip scrolls sideways when there are many). There is **no table of languages below, no row to click, no Side by side switch and no Reference/Editing dropdowns** (all removed on request): every language is editable at once. The head of each panel has the language, its publish **status** badge and an "n problems" badge when it has problems; its foot has the `wa_template_name`, "Unsaved changes", Revert and Save. Unsaved edits of every language are kept in `ui.drafts` at the same time. The **+ Add language** dropdown is in the toolbar (left); the new panel is added at the end of the strip and scrolled into view.
- **The right sidebar shows history or comments** (one at a time, see Comments). **History has exactly two tabs**, hidden by default ("Show history" in the toolbar, "Hide" in the sidebar heading): **Content** (first, the default) and **Other** (`ui.histTab`; the choice stays when you work in another language panel or pick another template). There are **no language tabs, no Reference/Editing tabs and no separate Tree tab** (an explicit decision: the languages are named on the lines instead, e.g. "English · text → …"). **Content** is the tree of content changes with **one line per step (what, who, when)**, see "Rewinding" below. **Other** is the plain linear list (one after the other, newest first, with a language chip where there is one) of all activity that is **not a content change**: published, renamed, blocked/unblocked, timing changed, copied/moved between campaigns (`Store.historyFor(id, 'activity')`). Tab labels carry no counts. There is deliberately no History page tab, no language filter dropdown, no highlight on a panel, and nothing inline in the panels. Updating the sidebar must never re-render the textarea (it would lose the caret). The sidebar is wider while Content is shown: the layout class `tree-on` (a 520px history column) is set **only while the history pane exists and its Content tab is active**; `updateHistoryPane()` runs on every keystroke (via `syncDirty`) and used to add `tree-on` even with the pane closed, which halved the editor (regression test in `core.test.js`). The page itself never scrolls: `#app` is a full-height flex column and `.layout` fills what the top bar leaves (only the editor and the sidebars scroll inside it).
- **Status per translation:** `draft` (never published), `deployed` (= published), or `modified` (**any** template part edited after the last publish: body, placeholder defaults, header media or type, footer, buttons; the status compares a signature, so restoring the published values makes it Published again; the old `wa_template_name` is kept until published again). Data published before parts existed (no `deployedSig`) is compared by text only.
- **Block template approval** is a name-level flag. While on, Publish all does nothing for that content. It cannot be turned **on** once any language of the name has been published (`waName` set); the checkbox is **not shown at all** for such names (removed, not disabled) and `Store.setBlocked` rejects it. Turning it off is always allowed.
- **CSV:** `name,language,wa_template_name,text`, one row per name × language, UTF-8 with BOM (added at download time) so Excel reads Hindi/Kannada correctly. `text` is the **authored body with named placeholders** (`{{name}}`), not the WhatsApp-numbered one. Header, buttons and footer are not in the CSV. There is **no JSON download in the UI** (removed on request); `Store.toExtraContent` stays for the orchestrator parity tests.
- **One editor toolbar** (template editor, no header block above it): the **+ Add language** dropdown on the left, and on the right **Block template approval**, the **comments icon**, **CSV**, **Show / Hide history** and **Publish all** (its label has no count; the tooltip says how many languages it will publish). Only the blocked banner can appear above it.
- **No name heading in the template editor:** the template's name heading and the description line under it (name base, language count, campaigns) were removed on request; the name is in the list on the left and **Rename** is a **pencil on each list item** (hover/focus; click turns the name into a text box in the item with ✓ / ✕, Enter saves, Esc cancels; the pencil also selects that item). Flows keep their heading and Rename button. Tests read the open template from the selected list item.
- **Name rules:** the template name is derived from the content name (lowercase letters, digits and underscores), so two names that map to the same slug are rejected.
- **Campaigns sidebar (far left):** layout is four columns: campaigns | content names | editor | history. The campaigns list is **All content** plus one button per campaign name (no counts). Picking a campaign filters the content-name list to that campaign (the search box filters within it; the list title shows the campaign name); if the open content is not in it, the first content of that campaign opens, and an empty campaign shows an empty state in the editor. Model: `state.campaigns = [{id, name}]` and each content has `campaignIds` (an array: a template can be in **several** campaigns, or none; data saved with the older single `campaignId` is converted by `migrate()`). New content is filed under the selected campaign, or under none when **All content** is selected (such content only shows under All content). The content header shows `Campaign: <name>` / `Campaigns: <a>, <b>`. **Adding campaigns:** a **+** icon button sits beside the "Campaigns" title; clicking it opens a text box (with the + icon and an **Add** button) in the same spot, and the box closes when it loses focus (Escape, Tab away or clicking elsewhere), the same pattern as the content list's boxes (own state `ui.campBox`, own `#camp-tools`, own `focusout` handler; only one box is open at a time). Enter or Add calls `Store.createCampaign`: the name is trimmed, required and unique case-insensitively (errors show under the box); the campaign is appended, **selected**, and recorded with `createdAt`/`createdBy` (not shown anywhere yet). There is **no UI yet to rename or delete campaigns** (the sample campaigns come from `SAMPLE_CAMPAIGNS` in `store.js`; `migrate()` adds them to data saved before campaigns existed). The **CSV deliberately has no campaign column** (columns stay `name,language,wa_template_name,text`).
- **Drag a template onto a campaign (copy / move):** each content item has a **grip handle (⋮⋮) on its left, and only the handle is draggable** (the row itself is not, and the whole row is shown as the drag image; clicking the handle just selects the item). Dropping on a campaign button (not on "All content") opens a modal dialog (`#modal-root`, `role="dialog"`; Esc / backdrop / Cancel close it, Tab is trapped inside, focus starts on the first enabled option). The dialog shows, **above the options, a non-interactive list headed just "Already in" (no "read-only" text) of every campaign the template is already in** (the target is marked "(this campaign)"; "Not in any campaign yet" when empty), then the options **Copy, Move, Cancel**, each with a one-line description of what will happen. Rules live in `Store.planDrop(contentId, targetId)` (DOM-free, tested in Node): **Copy** adds the target and keeps the other campaigns (disabled if already in the target). **Move** takes the template out of its one campaign and puts it in the target. **If more than one campaign owns the template, Move is disabled and its label becomes "Can't move"** (with the reason, naming the owners and suggesting Copy), whichever view you dragged from; it is the same for 2, 3, … owners. A template in exactly one campaign dropped on that same campaign disables both Copy and Move ("Already in …"). Copy means "same template in another campaign", not a duplicate, so editing it changes it everywhere. Each copy/move is logged (`campaign_copied` / `campaign_moved`, shown in the history sidebar's **Other** tab with who and when). Drag-and-drop is mouse-only (HTML5 DnD: no touch, no keyboard alternative yet). Flows have their own four-option dialog (see Flows).
- **Left bar tools:** at the top there are two icon buttons, **search** (magnifier) and **new** (+). Clicking one opens its text box in the same spot, keeping that icon inside the box (the + box also has the **Add** button). The box **closes when it loses focus** (click elsewhere, Tab away, Escape). Search: the filter stays applied after the box closes and is shown by an accent-coloured icon plus a "Search: “…” ×" chip; Escape or × clears it. New: a half-typed name and its error are dropped on close; Enter or Add creates it and closes the box. Implementation gotchas (both bit us): removing a focused element fires `focusout`, so re-rendering the tools area is wrapped in a `rerendering` flag and typing never re-renders the text field; and Add/× have a `mousedown` `preventDefault` so the field does not blur (closing the box) before the click lands. Only the tools area is re-rendered on open/close, never the list, so a click on a list item is not lost.
- **Theme:** colours are CSS variables in `style.css` (`:root` = light, plus two identical dark blocks: `[data-theme="dark"]` and `prefers-color-scheme: dark` when there is no `data-theme`). A three-way **Light / System / Dark** switch sits at the left of the top bar; System (default) means no `data-theme` attribute and follows the OS. The choice is stored in `localStorage` key `cms-prototype-theme`, and an inline script in `index.html` applies it before first paint. Never hard-code a colour in CSS or JS; add or reuse a variable and give it a value in both themes (white text on the filled blue/green buttons is the only literal colour).
- **Rewinding (the Content tab, an undo tree like Emacs' undo-tree):** the sidebar shows **content in a tree (Content tab) and everything else as a plain list (Other tab)**. Content steps (`content_created`, `text_edited`, `part_edited`, `language_added`, `header_type_changed`, `rewound`; `Store.isContentStep`) are the nodes of the **Content** tab; all other activity (published, renamed, approval block, campaigns, timing) is the linear **Other** tab. Every content event has `parent` = the node that was current when it happened, `snap` = what the template looked like right after it, and `Content.head` = the current node; the tree link of a step is its nearest *content* ancestor (a publish or rename in between is skipped) and the "current" marker sits on the nearest content step at or above `head`. The tree (sidebar widens for it) is drawn newest first like `git log --graph` (`Store.historyTree`: DOM-free, tested; lane colours are `--lane-0..5` theme variables) with **one line per step: what, who, when** (a snippet of the new text for body and footer edits). The current step has a "current" chip and a bigger dot; a "Rewound" step has a hollow dot. **Details** on a line (several can be open; `ui.treeDetails`) opens a panel under it with the full title, kind, who and when, and what changed (the word diff or before → after, the same body the language tabs show), and says why the step cannot be rewound to when that is the case; the lanes keep running through an open panel. **Rewind** (button on hover/focus, keyboard reachable, opacity not visibility) calls `Store.rewind(contentId, eventId)`: the template goes back to that step's snapshot and **the rewind is logged as a new step** (`rewound`, `from`/`to`) whose parent is the step you went back to, so **nothing is ever deleted**: the steps after it stay as another branch, they can be rewound to as well, and editing from here grows a new branch (branches show as extra lanes joining at the step they left). `Store.rewind` refuses a non-content step. What a rewind restores: the header type and, per language, body, header file, footer, placeholder defaults, buttons. **Not restored:** name, campaigns, timing, the approval block, publish bookkeeping (publishing is external; status just follows the usual signature rule, so rewinding to the published content shows Published again). A language added after the step stays but is emptied (there is no deleting a language). One save that changes several parts makes one step per part, each with its own snapshot. Rewind is **disabled** (reason as tooltip) while the template has unsaved edits, for a step that looks exactly like now, and for steps saved before rewinding existed (migration chains them, makes the newest the current step with a snapshot of today; older ones are listed but cannot be restored). Flows have no tree.
- **Comments** (templates and flows; `state.comments`, `Store.addComment` / `setCommentResolved` / `commentsFor` / `locateComment`, DOM-free and tested): a comment is about the **whole template or flow**, a **part** of a template in one language (**body, header, footer, a button**) or, for body / footer / button text, a **selected piece of text** (kept as `quote` + `start`/`end`; the header and whole parts have no quote), or a **node** of a flow. A **comments icon button** (speech bubble, no text; the open count is a small badge and in its label) in the header of every template and flow opens the **right sidebar in comments mode** (the same sidebar as history, **one at a time**: Show / Hide history, always in the editor toolbar as a toggle, swaps it back; `ui.commentsOpen`). At the **top of that sidebar** sits the composer: a **"Comment on" dropdown** (whole template, then per language its body / header / footer / each button; on a flow: whole flow and every node), a text box (1-1000 characters, **Ctrl/Cmd+Enter** adds) and **Add comment**; text you **select in the body, footer or a button's text** is picked up as you select it and shown as a quote chip (× keeps the part and drops the quote; only a selection in the field you are in counts, never typed text), and a flow node's **💬** (visible on hover, always when it has open comments, with the count) opens the sidebar aimed at that node without starting node edit. A half-written comment survives re-renders (`ui.cmDraft`). Under the composer the sidebar lists the comments as **message pills** (rounded bubbles: where, quote, text, who and when) with two tabs: **Open** (default, newest first) and **Resolved** (most recently resolved first, with who and when, **Reopen**); **Resolve** moves a comment from Open to Resolved, so resolved comments are hidden from the default list. Each item shows author, time, where (language · part, or the node's name), the quote (with a note when the text has **moved** or **changed/been removed** since: `locateComment` against the text as it is in the editor now, unsaved edits included), the comment, and **Go to** (focuses the field and selects the quote; for a node scrolls to it and flashes it). Parts with open comments carry a **💬 n** badge on their label. A comment on a removed node stays and keeps the node's old name. **Comments are not history steps** (nothing in the history or the Content tree) and **rewinding does not touch them**. Open comments are per template and per flow (a template that is a flow by itself shows its own). No replies, no editing or deleting of comments yet; one user (`CURRENT_USER`). Not in the CSV export.
- **Language codes** follow Turn.io/WhatsApp (`TURNIO_MESSAGES_API.md`, Appendix B).

### WhatsApp template parts (header, body placeholders, buttons, footer)

Modelled on the orchestrator's `extra_content_schema` in `~/repos/sms-ivr-orchestrator/campaign/models.py` (`validate_extra_content` is the reference). Everything is **per language** except the header *type*.

- **The editor shows only the Body by default.** An **+ Add…** dropdown (just below the phone) adds a **Header** (Image / Video / Document), a **Footer**, a **Quick reply** button or a **URL** button. Options already present or at their limit stay listed but disabled, with the reason. Sections with content always show (so existing templates show everything they have). Each added section has a remove control (header: **Remove header**; footer and buttons: ×) (an added-but-empty footer is not an unsaved change, so Save/Revert stay disabled until it has text; **Revert** after typing forgets the added section). A freshly added button shows its problems box until its text and payload/URL are filled in. Containers `data-sec="buttons|header-url|placeholders|button-details|problems"` always exist (empty) so they can appear while typing; never re-render the field being typed in.
- **Body = the named layer on top of WhatsApp's numbers.** Authors write `{{name}}`; WhatsApp needs `{{1}} {{2}}`. `Store.positionsOf(text)` gives `name -> [positions]` (one number per *occurrence*, like the orchestrator's `get_body_params_map`), `Store.whatsappBody(text)` the numbered body (used for the export and tests; the editor no longer shows it, the Placeholders table shows each name's WhatsApp position instead). Names use the orchestrator's pattern `[a-zA-Z1-9_]` (**no digit 0**, no spaces); anything else inside `{{ }}` is a problem.
- **A name can fill several numbers**: use it more than once (max 5 uses, the schema's `maxItems`), or **rename another placeholder to it** (merge). The **Name column is editable**: committing (Enter/blur, not per keystroke) calls `Store.renamePlaceholder`, which rewrites every `{{old}}` in the body (whole placeholders only), carries the default over, and on a merge keeps the existing default (unless empty). Invalid names are refused with a toast. The same works for variables in a button URL.
- **Defaults**: every placeholder needs a default of 1-200 characters (`body_param_defaults`). Defaults of placeholders that left the text are dropped on save.
- **Header**: the *type* is one per name (`headerType`, the orchestrator's `ref_type`) and is changed immediately (a content step in the Content tab, marks published languages as edited); each language has its own **media link** (optional): an **https link to the file on the static CDN** (`extra_content.header[lang]` is that link; the orchestrator's `get_content_type` already treats a value starting with `http` as a URL, but its `validate_extra_content` still checks the value against TurnMedia, so confirm with the orchestrator team; the parity test stubs that lookup). Adding a header in one language adds it to every language.
- **Header media link and upload** (`Store.checkMediaUrl`, `checkFile`, `addMedia`, `newCdnLink`, DOM-free): **the prototype connects to nothing**, so the CDN is a dummy (`https://cdn.noorahealth.org/templates/…`) and **no link is ever fetched**. In the phone, the header is the picture (hover it: a **pencil** and, beside it in the corner, a **cross** appear at its top right, both keyboard reachable: the pencil opens the file dialog, the cross removes the header from every language like **Remove header** below the phone; there is **no Upload / Replace button**); the **type** dropdown, its limits and **Remove header** are **below the phone**, with the **media link** field (type or paste any link: a link the prototype has no file for is drawn as a **tile with the file's name**, the link as its tooltip; a half-typed link updates the tile at once). A **chosen file** is checked with WhatsApp's template-header rules (`HEADER_FILES`: **image** JPEG/PNG up to 5 MB, **video** MP4/3GPP up to 16 MB, **document** PDF up to 100 MB; a wrong type, empty or too big file is refused with a toast and the header is unchanged), is given a **randomly generated dummy CDN link** that keeps its extension (`/templates/<16 hex>.png|jpg|mp4|pdf`), its **data is stored in IndexedDB** (db `cms-prototype-media`, store `files`, key = the link, value = the file blob; read back into blob URLs a moment after start-up, so pictures appear just after a reload) and is **shown from that local data** (image, a video player, or a document row with name and size). Only metadata (`state.media[link]`: name, type, size) is in the main state; if IndexedDB is unavailable the file shows until the page closes (the note under the picture says it is not kept). The link is part of the draft like any other part (saved with Save). Problems (block publishing, not saving): the link is not an https link, or its extension says another kind than the header type (a link with no extension is accepted). **Reset demo data** empties IndexedDB. Sample headers are dummy CDN links.
- **Footer**: per language, up to 60 characters, no placeholders (WhatsApp's rule). It is **not in the orchestrator's schema yet** (its code reads `extra_content["footer"][lang]` but marks it FIXME), so the export includes `footer` only for languages that have one.
- **Buttons**: **at most 3 quick replies and 1 URL button** per translation. This is a product rule, **stricter than the orchestrator's schema (10 buttons)**; the export still validates. Quick reply: text 1-25, default payload 1-800. URL: text 1-25, URL 10-1000 characters and http(s); `{{name}}` variables in it need defaults (positions derived like the body's).
- **Consistency between languages** (`Store.consistency(content, partsByLang?)`; only languages that have text are compared, an empty translation is ignored). **Errors** (they join the language's own problems in the editor's Problems box and in the panel head's "n problems" badge, and **block publishing of every language** of the name: `canDeploy` says "n mismatches between languages to fix before publishing", Publish all is disabled; **saving is never blocked**): the **number of buttons** differs, the **type of buttons** differs (compared position by position), a **header media** is set in some languages and missing in others (only when the name has a header), a **footer** is set in some and missing in others. **Warnings** (a separate Warnings box, they do not block): a placeholder name used in some languages but not in others (placeholder defaults are not compared). The editor passes the unsaved drafts of all languages, so the box updates while typing; publishing looks at saved parts. The Hindi sample of Welcome message has a header media so the sample is consistent.
- **The editing panel IS the phone (no Preview button, no preview dialog; removed on request).** Each language is edited in place as WhatsApp shows it (`phoneShell`, the same markup as the node preview): sender header, chat background, **one bubble** with the **header media** on top, the **body** as a text box (auto-grows with its text), the **footer** as a small text box (+ remove ×) and the time (with the body counter), and the **buttons under the bubble** with their text typed on the button itself (counter, ×). **Everything that is not part of the picture sits below the phone**: the **header type, limits and media link**, the **Body placeholders** table (names, positions, defaults), the **buttons' payloads / URLs** (and URL variables), **each field labelled with its button's own text** (updated as you type it in the phone; no "quick replies 1 / 3 · URL 1 / 1" count: the limits live in the + Add dropdown) and the **Problems / Warnings**; the **+ Add…** dropdown is **just below the phone** (not inside it); in the phone the buttons sit right under the bubble, a pixel apart, like WhatsApp draws them; Save / Revert stay in the panel foot. There are no section labels inside the phone. **A language panel is as wide as its phone plus 80 px** (`--panel-w: 420px` for the panel, 340 px for the phone, every language's phone alike; every language is an editing panel; everything below the phone fits that width, so several languages fit next to each other). **Every phone has a constant height** (`--phone-h: 580px` in `style.css`, a bit shorter than an average phone; every language's phone and the flow-node phone alike): a long message does not stretch it, the chat scrolls inside it, and a short one does not shrink it. Limits of a text box (not WYSIWYG): the body shows the authored `{{name}}` (not the default value filled in) and WhatsApp's `*bold*`/`_italic_` are shown as typed; the read-only phone (the flow node preview) does fill the defaults (highlighted; one without a default stays `{{name}}`, marked) and renders `*bold*`, `_italic_`, `~strike~`, ```` ```mono``` ```` and line breaks (`waBodyHtml`). Containers: in the phone `data-sec="header|body|footer|buttons"` (and `add` just below it), below it `"header-url|placeholders|button-details|problems"`; the phone's buttons are `.bcard.wa-btn-edit`. Colours are theme variables (`--wa-*`, `--phone-frame`) with light and dark values.
- **Problems** (`Store.problems`) are listed under the editor only when there are some, and **block publishing** (`canDeploy`; "Publish all" skips such a translation and says so; the language panel's head shows "n problems"). Saving is never blocked. An empty body is a problem with `code: 'empty'` that the editor deliberately does not show for a new translation (publishing is already refused for empty text).
- **Drafts** hold *all* editable parts of a translation (`ui.drafts`), so switching language keeps unsaved edits (dot on the table row). Saving writes one history event per changed part (`text_edited`, or `part_edited` with a `detail` of Header / Footer / Placeholders / Buttons) with before/after text and a word diff.
- **extra_content shape** (`Store.toExtraContent`; **no button in the UI any more**, kept for the parity tests): `{header, body_param_defaults, body_param_positions, buttons[, footer]}` with every key per language, exactly the shape `validate_extra_content` expects. It is checked in `tests/unit/orchestrator-parity.test.js` against the orchestrator's real validator.
- **Known orchestrator quirks** (pinned by tests; confirm with the orchestrator team): its placeholder regex `[a-zA-Z1-9_]+` excludes `0` (so `{{item0}}` is not recognised); and `get_template_vars("{{a}}{{b}}")` returns only `['b']` because of a repeated regex group (adjacent placeholders lose all but the last), where the prototype keeps each. Not modelled: the `"default"` language key in `header` / defaults / buttons, and the `body` example values used when a template is created.

### Flows (second tab of the content sidebar)

The content sidebar has two tabs, **Templates | Flows**. The Templates tab is the original list. A **flow** is a **graph on a canvas**: nodes joined by edges. The timing ("N days before/after ref date") is on the flow, not on nodes (see Timing below).

- **Model** (`store.js`): `Flow = {id, name, campaignIds, nodes: [...]}`. Every node has `id, x, y`. Types: `template {templateId, next}`, `logic {title, outs: [{id, label, to}]}`, `action {name, definition, next}`, `input {title, next}` (plain, numbered "Input N", nothing to edit), `flow {flowId, next}` (calls another flow). Non-logic nodes have one outgoing `next`; a logic node has any number of named outgoing edges (at least one). Every node can have any number of incoming edges (including input nodes). Edges can't form a loop (`reaches`); connecting a node that already has an edge replaces it. A flow can be in several campaigns, like a template. Flow names are unique and **cannot equal a template name** (single templates are listed as flows too). Data saved with `steps` is converted to a chain of template nodes by `migrate()`; node timing from earlier saves is dropped.
- **Node types**: **Template** (a template used once per flow, with optional **placeholder values for this flow**, see below; **using a template in a flow never changes which campaigns the template is in**. A template listed in a campaign stays listed there as a single-template flow unless a flow of that same campaign includes it; changing a node's template can make the old one a single-template flow there again), **Logic** (starts with two edges "Condition 1/2"; edge names unique per node, 1-40 chars), **Action** (name unique among the flow's node titles, up to 60; definition up to 500), **Input** (a plain box), **Flow** (calls another flow: never itself, never the same flow twice in one flow, never a flow that already calls this one directly or through others). Calling a flow does not move or copy it into this campaign.
- **Toolbar**: `+ Template…` and `+ Flow…` are **searchable pickers** (button + popover with a search box; type to filter, arrows + Enter, Escape or an outside click closes; options that can't be chosen stay listed, disabled, with the reason: "already in this flow", "calls this flow"), then `+ Logic`, `+ Action`, `+ Input`. New nodes land on the first free slot of a 3-column grid.
- **Nodes are read-only by default** (text only, no inputs). An action with no definition shows only its name (no empty definition area). **Click a node (template, flow, action, logic, input) to edit it**: its fields appear with a **✓ save** and **✕ cancel** at the extreme right of the node header. **While a node is being edited nothing else can be used**: clicks, drags, focus and Tab outside it are blocked (capture-phase handlers in `app.js`), the node shakes and a toast says "Save (✓) or cancel (✕) your changes to this node first". Editing happens on a draft (`ui.nodeEdit`); nothing reaches the store until ✓. **Enter** saves from a single-line field, **Ctrl/Cmd+Enter** from the definition, **Escape** cancels (first press only closes an open picker). If the store refuses (duplicate name, empty condition…), a toast explains and the node stays in edit mode. A logic node's name is saved with its conditions in the same atomic `Store.updateLogic(flowId, nodeId, outs, title)` (logged as `flow_logic_renamed`). Logic edges are edited as a list with remove (disabled at one left) and `+ Add outgoing edge`, saved atomically (`Store.updateLogic`: existing ids keep their connection). A click right after dragging a node does not open it. **Names are edited in the header**: for input, logic and action nodes the label in the node's header turns into the text field when the node is clicked (input: nothing below it; logic: the condition list; action: the definition box). An action's name is shown in the header in view mode too, and its body is just the definition (nothing at all when it has none). Names are unique among the flow's node names, required, up to 60 characters. Input names: (`Store.renameInput`: required, up to 60 characters, unique among the flow's node names, logged as `flow_input_renamed`).
- **Interaction**: drag a node by its header (mouse only, pointer events, saved, not a history event); drag from the dot on a node's right edge (one per condition on a logic node) onto another node to connect. Edges are curves ending at the target's input dot, with **no label on the edge** (a logic node's conditions are shown on its own rows, next to their dots); each edge has a pill that holds only a disconnect × (its aria-label names the edge). **Hover** an edge (its line or pill; the line has a wide invisible hit area, and the part under a node can't be hovered) highlights it (accent colour, 4px instead of 2px) and only then shows its pill with the ×; **hover** a node outlines it (accent outline). A node's own corner × (remove) is also visible only on hover and is hidden while editing.
- **Placeholder values per flow**: a template node can override the template's placeholder defaults **for this flow only** (`node.values = {name: value}`; the template and other flows are untouched). In the node's edit mode there is **one field per placeholder name, the union over all languages of the template** (a name used in several languages is one value), with the template's own default as the hint; **blank = use the template's default** (not stored). Up to 200 characters each. View mode shows only the values that are set. Picking another template in edit mode swaps the fields (the original's values come back if you pick it again); saving a template change clears the old values. Saved together with the template choice by `Store.updateTemplateNode` (atomic, logs `flow_values_edited` with before/after). A duplicate copies the values.
- **Live phone preview beside a template node in edit mode**: a read-only WhatsApp phone appears to the right of the node while it is being edited (it is part of the editing node, so the edit lock allows it) and disappears when it is saved or cancelled. It shows the message with the draft's placeholder values over the template's defaults, updates as you type or pick another template (the typing field is never re-rendered), and has small language buttons (default: the first language with text). Same phone markup as the Preview dialog (`phoneHtml`).
- **Direction toggle** (flow toolbar, **→ Left to right | ↓ Top down**, saved per flow in `Flow.direction`, layout only, not in history): left to right = input dot on a node's left edge, output dot on the right, edges leave sideways; top down = input dot top centre, output dot bottom centre, edges leave downwards (a logic node shows its conditions side by side along its bottom, each condition's dot sitting on the node's bottom border; while a logic node is being edited its dots stay beside the edge rows). Each direction **keeps its own layout** (`x,y` = current direction, `alt` = the other): the first time a direction is used the nodes are laid out in layers following the edges (`autoLayout`), after that whatever you moved is remembered; switching back restores the original exactly. The arrowhead has a fixed size (`markerUnits="userSpaceOnUse"`), it does not grow when an edge is hovered.
- **A template that is in no flow of a campaign is itself a flow there** (derived, not stored: `Store.isImplicit`). The Flows tab lists the flows you created and each such template **with an indicator**, in the shared order (by default the flows first, then the templates) (the "Single template" pill, tooltip "This template is itself a flow"). Under **All content** a template is listed when it is alone in any of its campaigns, or has no campaign and no flow. Adding a template to a flow takes it out of that campaign's single-template list; removing it puts it back.
- **Timing is per flow** ("Sent `<n>` days before/after `<reference date>`"): `Flow.timing`, **dummy default 7 days before expected_date_of_delivery**, edited in a card above the toolbar (`Store.setFlowTiming`; each change is a `flow_timing_edited` event in the flow's history; a duplicate copies it, flows saved before get the default). Nodes carry no timing. A template that is a flow by itself has its own (`Content.timing`, `setTemplateTiming`, card above the template editor, history under **Other**). Rules for both: whole days 0-999, `before`/`after`, a reference date chosen from a **dropdown** (`Store.REF_DATES`: `expected_date_of_delivery`, `date_joined`, `baby_dob`, `date_of_birth`, `registration_date`, `discharge_date`; add new ones there). The store itself still accepts any variable-style name, so a value saved earlier that is not in the list stays selectable until another is chosen. `0` days reads "on `<ref>`". Edits commit on Enter/blur and are validated (toast and reset on error). The Flows list entry shows the timing, then what the flow holds.
- **Creating**: with the Flows tab open the **+** creates a flow in the selected campaign (or none under All content) and opens it. **Every entry of the Flows list can be reordered by dragging its grip handle** (mouse only): the flows you created and the templates that are flows by themselves move among each other in **one shared order** (`state.flowOrder`, keys `f:<id>` / `t:<id>`; each campaign shows its entries in that order; new entries start after the ordered ones, flows first). The before/after marker depends on the half you drop on. `Store.reorderFlowItem(kind, id, targetKind, targetId, place)` (`reorderFlow` is the flow-to-flow shortcut); it logs `flow_reordered` on a flow and `flow_list_moved` under a template's **Other** history. Dropping on a campaign still opens the Copy/Move or Refer/Duplicate/Move dialog.
- **Dragging a flow onto a campaign** (by its handle) opens a dialog with **four options: Refer same flow, Duplicate flow, Move flow, Cancel** (templates keep Copy / Move / Cancel), with the "Already in" list above. **Refer same flow** = the one flow is also in the target (disabled if already there). **Duplicate flow** = a new independent flow named `<name> (copy)` / `(copy 2)`… with the same nodes, edges, layout (new ids), placed right after the original, always available. **Move flow** = it leaves its campaign (**"Can't move"** when more than one campaign owns it). **Templates come along** on all three: Refer and Duplicate add them to the target; Move moves the templates only this flow uses in the source, while a template another flow of the source still uses stays there (and is also added to the target). Flow-call nodes keep pointing at the same flows. A single-template flow is dragged exactly like a template. `Store.planFlowDrop` / `referFlow` / `duplicateFlow` / `moveFlow`.
- **History**: a flow has its own timeline (one **Flow** tab; **Show history** is in the flow header): created (a duplicate says "Duplicate of …"), renamed, node added/removed, template or called flow changed, edges connected/disconnected (read like "Logic 1 [Replied yes] → Action 1"), conditions added/renamed/removed, action renamed/changed, moved in the list, shared with / duplicated to / moved to a campaign. Events carry `flowId` (no `contentId`), so flow events never mix into a template's history.
- **Not built**: deleting a flow, comments on a flow's edges, removing a flow from a campaign other than by Move, flows in the CSV export, keyboard or touch dragging, anything that actually schedules or sends, an undo for node removal.

## Tests (`tests/`)

Dependency-free: Node 22+ built-in `node:test`, plus Chromium/Chrome for the browser suites and python3 + an orchestrator checkout for the parity tests (anything unavailable is **skipped with a reason**, never passed). See `tests/README.md` for the file map and how to write one.

- **Commands**: `npm run test:unit` (about a second), `npm run test:ui` (browser suites **in parallel**, about 20 s), `npm test` (unit + ui, parallel), `npm run test:serial` (the same one at a time, for chasing a flaky check), `npm run test:flows` (the **Flows UI suite, kept out of `test` / `test:ui` on request: not run for the time being**, `tests/flows/`), `npm run test:watch` (unit tests re-run on save); the plain equivalents are `node --test tests/unit/`, `node --test --test-concurrency=4 tests/ui/`. One file: `node --test tests/ui/drag-drop.test.js`. By test name: `node --test --test-name-pattern="drag" tests/ui/`.
- **Run the FULL suite only after the user confirms** (standing instruction: it takes several minutes). On your own, run just what is relevant: **always `npm run test:unit`** (about a second) **plus only the UI file(s) for the area you changed**. Do not run `npm test` or `tests/ui/` as a whole unprompted; when a full pass seems warranted (a broad refactor, a milestone), ask the user and let them decide.
- `node --test tests/unit/` (about a second): `tests/unit/store.test.js` (data rules, no browser) and `orchestrator-parity.test.js` (runs the orchestrator's own `validate_extra_content` / `get_body_params_map` through `tests/support/repo_validator.py`).
- `tests/ui/*.test.js` (about 20 s in parallel; each file has its own Chromium on a free port, so they never collide; the driver waits for the page / for an action to settle instead of sleeping fixed times, so **never add a fixed `sleep` after an action**, use `b.settle()` or wait for the condition) drive the real page through the DevTools protocol (`tests/lib/cdp.js`) with **real** mouse, keyboard, text input and drags, so focus/blur and mousedown-vs-click behave as for a user. A suite fails on any console error.
- **Rules for changes:** every behaviour change comes with a test in the same change (rule in `store.js` -> unit test; anything about focus, clicking, dragging, dropdowns -> UI test). Update the test when a decision changes (the old expectation is the spec being replaced), never loosen it to make it pass. A new check should be shown to fail first (break the code, see it go red). When a UI check fails, first ask whether the *test* clicked something off-screen or at the wrong time (the driver scrolls targets into view) before changing the product.
- Gotchas learned the hard way: removing a focused element fires `focusout` (see Left bar tools); `<select>` choices are driven in tests by setting `.value` and dispatching `change`; a history diff renders removed and added words back to back (`namefirst`), so assert on stable words.

## Commits

**Commit after every safe checkpoint, without waiting to be asked** (standing instruction from the user). A safe checkpoint is a coherent change that works, with the **relevant tests green**: always the unit suite plus the UI suite(s) covering what changed (the full suite only when the user has confirmed a run, see Tests). Examples: a finished feature, a completed refactor, a fix with its test. State what was run in the commit message body (e.g. `Tests: unit + ui/drag-drop; full suite not run`). If tests cannot run (no Chromium, no Node 22), say so in the commit message and in the summary instead of silently committing.

- Run `git status` first and stage the intended files **by name** (never `git add -A` blindly). Never commit scratch output, screenshots, downloaded files or editor/OS junk; tests write only to temp directories.
- One logical change per commit, imperative summary line (what), then a short body (why, and anything non-obvious such as a decision, a limit or a known quirk).
- End every commit message with the trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` (use the model attribution line given in the session's instructions).
- Do not commit failing tests or half-finished work; if you must pause mid-change, leave it uncommitted and say what is left.
- Commit locally only. There is no remote; do not add one or push unless the user asks.
- **Commits are GPG-signed** (`commit.gpgsign=true`) and the passphrase prompt needs the user. If signing fails or times out (`gpg: signing failed: Timeout`), **do not** use `--no-gpg-sign` or change git config. Leave the work staged, save the message to a file, tell the user, and retry once they have unlocked the key (the agent keeps it for a while, so several commits in a row usually work).
- A new rule from the user that changes how we work goes into this file in the same commit as the change it affects.
